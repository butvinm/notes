# Notes v1: local personal knowledge system with CLI, SQLite index, schedules, and Claude Code integration

This plan supersedes `DESIGN.md`. It carries every normative decision from the design forward, so the design file is removed in Task 1 and this document becomes the single reference during implementation.

## Overview

`notes` is a local personal memory system for a developer and their agents. It solves four related needs:

- preserve decisions, facts, promises, events, reminders, and additional context as plain Markdown files;
- find and surface relevant entries while working on a project or task, from the CLI or through a Claude Code hook;
- deliver scheduled notes as desktop notifications and explicitly track when they have been read;
- work equally well from the CLI, through Claude Code, or manually in any editor without an agent or network connection.

The system is personal-first. It does not depend on a team process, well-maintained tracker issues, or a shared agent harness. Every note is a regular Markdown file that can be opened in any editor and versioned with Git. `session-log` (a separate tool) remains the working memory of a long session; durable decisions, facts, and promises graduate from a session log into `notes`.

Design principles that every task must respect:

1. **Markdown is the source of truth.** Content, metadata, schedules, and relationships live in files. SQLite is derived, except for device-local delivery and read state.
2. **SQLite is the only internal engine.** It stores the index, full-text search data, relationships, and local notification state. No separate search server, cloud database, or daemon.
3. **One vault and one CLI.** The vault always lives at `~/.notes`. The user, skills, hooks, and scheduler all invoke the same `notes` executable. No vault registry, no current-directory discovery, no multi-vault support in v1.
4. **Local-first and offline-first.** Editing, search, schedules, and notifications work without a network connection or agents.
5. **Agents improve the experience but are not dependencies.** Every core CLI operation works without an agent. Agent-assisted drafting uses a configurable generator command, Codex by default.
6. **Keep the model minimal.** New note kinds, relationship types, and states appear only for demonstrated use cases.

## Solution Overview

A single Python package `notes` exposes a `click` CLI. Every command that operates on an existing vault first runs a fast incremental sync from Markdown into SQLite, then does its work. Commands that change Markdown write the file first and update the index second, so an interrupted process is repaired by the next command. Valid changes to versioned files are committed to Git automatically; SQLite-only changes (`tick`, `read`) are not.

Search is SQLite FTS5 over pre-normalized text (Russian lemmatized with `pymorphy3`, Latin stemmed by the FTS5 porter tokenizer), combined with exact tag and issue-ID matches that are weighted above ordinary text matches; a `paths` entry matching the current directory boosts recall but is never a match by itself. `notes recall` produces a bounded, deterministic block for the Claude Code hook: unread deliveries, then exact matches, then the best text matches above a threshold.

Schedules live in frontmatter in a canonical absolute form. A `systemd --user` timer runs `notes tick` every minute; `tick` creates at most one delivery per due note per run, shows a desktop notification, plays a sound once, and records the delivery in SQLite. `notes read` closes a note's unread deliveries. Read state is device-local and never enters Git.

Agent-assisted drafting is a CLI feature, not a skill feature: `notes draft create <kind>` composes the vault-owned prompts with a JSON context packet, calls the configured generator command, and stores the result under `~/.notes/drafts/` until `notes draft save` turns it into a note. A Claude Code plugin in this repository provides the `UserPromptSubmit` hook and the four skills; the skills are thin because the CLI owns prompts, validation, and persistence.

## Technical Details

### Vault

`notes init` creates the single vault at `~/.notes`:

```text
~/.notes/
+-- notes/                     # all notes, flat, no grouping by year or kind
+-- types/<kind>/prompt.md     # what the agent should capture for this kind
+-- types/<kind>/template.md   # mechanical scaffold used by `notes new`
+-- prompt.md                  # shared drafting prompt
+-- config.toml
+-- index.sqlite               # ignored by git
+-- drafts/                    # ignored by git
+-- .gitignore
+-- .git/
```

- The vault root is resolved by one function, `vault.root()`, returning `Path.home() / ".notes"`. Tests redirect it by setting `HOME`.
- A directory is a vault when it contains `config.toml` and `notes/`. Commands other than `init` fail with "no vault at ~/.notes, run `notes init`" when it is missing.
- Mutable properties (project, `kind`, `status`, tags) never determine a file's location. Notes may live in subdirectories of `notes/` because IDs are paths, but `notes new` always writes into `notes/` directly.
- Versioned files: everything except `index.sqlite`, its `-wal`/`-shm` companions, `drafts/`, and `embeddings/` (reserved for a future embedding cache). The packaged `gitignore` lists exactly these.

`config.toml` (packaged template, `auto_push` substituted at init):

```toml
[generator]
command = ["codex", "exec", "--skip-git-repo-check", "--ephemeral", "--sandbox", "read-only", "--color", "never", "-"]
timeout_seconds = 300

[git]
auto_push = false
remote = "origin"

[notifications]
sound = true
sound_id = "message-new-instant"

[recall]
limit = 10
min_score = 1.0
path_boost = 2.0
```

Unknown keys are ignored; missing keys take the defaults above. `defaults_version` is recorded in `~/.notes/.defaults-version` at init.

### Note format

The vault-relative path is the stable user-facing ID: `notes/2026-09-02-project-atlas-kafka-task-updates.md`. Filename and title are deliberately different: the filename carries the creation date and a short slug, the first `# H1` carries the complete natural-language title. Frontmatter has no `title` field.

```markdown
---
kind: decision
status: active
paths: [~/Dev/exampleco/project-atlas]
tags: [ATLAS-27, project-atlas, sync-worker]
keywords: [Kafka, tasks, runs, launches, jobs, Atlas, Project Atlas, proxy]
references:
  - CLAUDE.md
  - <tracker issue>
schedule: at 2026-09-09T10:00:00+03:00
related:
  - relation: supersedes
    note: 2026-08-27-project-atlas-websocket.md
---

# Project Atlas task updates over Kafka

**Decision:** ...

**Rationale:** ...
```

Parsing (`document.py`):

- Frontmatter is the block between a `---` line at file start and the next `---` line, parsed with `ruamel.yaml` round-trip loader. The body is everything after it. The H1 is a line starting with `# ` outside fenced code blocks.
- `Note` dataclass: `path` (vault-relative), `kind`, `status`, `title`, `body`, `paths`, `tags`, `keywords`, `references`, `schedule` (parsed), `related` (list of `Relation(relation, target_path)` with targets normalized to vault-relative), `content_hash`.
- Relationship targets in Markdown are relative to the current file (`2026-08-27-project-atlas-websocket.md` for two files in `notes/`), never prefixed with `./`. The parser resolves them against the note's directory; serializers convert back. Targets must stay inside `notes/`.

Validation (`document.validate(note, known_kinds, vault)`) returns a list of `ValidationError(line, message)`; a note with any error is invalid:

- the filename must be `YYYY-MM-DD-<slug>.md` with a real calendar date (`slug.creation_date_from_path` succeeds); `notes.created_date` is derived from it, and the error message points to `notes move` for renaming
- `kind` required and must be a known kind; `status` required and one of `active`, `archived`
- exactly one H1
- `paths`, `tags`, `keywords`, `references`: lists of non-empty strings when present; `~` in paths is kept as text (expanded at match time)
- `schedule`: canonical grammar only (see Schedules); required for `reminder` and `promise`; `promise` requires the one-shot `at` form (its due date)
- `related`: list of mappings with `relation` in `supersedes`, `child`, `related` and `note` resolving to an existing file under `notes/`; no self-relation; duplicates are an error
- unknown frontmatter keys are allowed (free-form metadata is fine)
- line numbers come from `ruamel` node positions for frontmatter errors and from the scan for H1 errors

Rewriting (`document.rewrite_frontmatter(path, mutate)`): loads the frontmatter with the round-trip loader, applies a mutation callback, dumps it back between the fences, leaves the body byte-for-byte unchanged. Used by `relate`, `move`, and schedule normalization.

Effective status: stored statuses are `active` and `archived`. `superseded` is derived: a note with any incoming `supersedes` relation has effective status `superseded` unless its stored status is `archived`, which always wins. The older file is never rewritten with status metadata. Notification state (`unread`/`read`) is not a note status.

Initial kinds and what their templates scaffold:

- `decision`: `**Decision:**`, `**Rationale:**` sections
- `fact`: `**Fact:**`, `**Source:**`, `**Context:**`
- `promise`: `**Promise:**`, `**Owner:**`, `**Due:**` (mirrors `schedule`), frontmatter `schedule:` placeholder
- `event`: `**What happened:**`, `**When:**`, `**Consequences:**`
- `reminder`: `**Remind me:**`, `**Why:**`, frontmatter `schedule:` placeholder
- `idea`: `**Idea:**`, `**Why it might matter:**`, `**Open questions:**`

Templates contain the frontmatter with `kind` and `status: active` filled in, empty `paths`, `tags`, `keywords`, `references` lists, and `# {title}`. Substitution is a plain `str.replace` of `{title}` and `{schedule}`; no format-string evaluation.

### Relationships

- `supersedes`: the current note replaces older knowledge; gives the target the effective status `superseded`
- `child`: the target is a child of the current note
- `related`: an association with no additional behavior

The index derives inverse directions (`superseded_by`, `parent`) in queries; they are never written to files. A true duplicate is merged into the canonical note and deleted; there is no `duplicate` relation. `notes relate` appends a relation; `notes move` renames a file and rewrites every outgoing and incoming relation target. Manual content editing needs no command.

The CLI renders an ID as a link followed by the title: `[notes/2026-09-02-x.md](/home/user/.notes/notes/2026-09-02-x.md) - Title`.

### SQLite

`~/.notes/index.sqlite`, WAL mode, `busy_timeout` 5 seconds because `tick` (systemd) and interactive commands may overlap.

```sql
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);           -- schema_version
CREATE TABLE notes (
  path TEXT PRIMARY KEY,                 -- vault-relative
  kind TEXT NOT NULL, status TEXT NOT NULL, title TEXT NOT NULL, body TEXT NOT NULL,
  schedule TEXT,                         -- canonical text or NULL
  paths TEXT NOT NULL, tags TEXT NOT NULL, keywords TEXT NOT NULL, refs TEXT NOT NULL,   -- JSON arrays
  created_date TEXT NOT NULL,            -- from filename
  content_hash TEXT NOT NULL, mtime_ns INTEGER NOT NULL, size INTEGER NOT NULL
);
CREATE TABLE note_tags (path TEXT NOT NULL, tag TEXT NOT NULL, tag_lower TEXT NOT NULL, PRIMARY KEY (path, tag_lower));
CREATE TABLE relations (src TEXT NOT NULL, relation TEXT NOT NULL, dst TEXT NOT NULL, PRIMARY KEY (src, relation, dst));
CREATE TABLE invalid_files (path TEXT PRIMARY KEY, content_hash TEXT NOT NULL, mtime_ns INTEGER NOT NULL, size INTEGER NOT NULL, errors TEXT NOT NULL);  -- errors: JSON [{line, message}]
CREATE VIRTUAL TABLE notes_fts USING fts5 (path UNINDEXED, title, tags, keywords, body, tokenize = 'porter unicode61 remove_diacritics 2');
CREATE TABLE deliveries (
  id INTEGER PRIMARY KEY, path TEXT NOT NULL, occurrence_at TEXT NOT NULL,
  delivered_at TEXT NOT NULL, read_at TEXT, UNIQUE (path, occurrence_at)
);
```

- `notes_fts` holds pre-normalized text (see Text normalization), one row per valid note.
- `deliveries` is device-local operational state and the only table that is not derived. A schema version bump drops and rebuilds every derived table but keeps `deliveries`. Deleting `index.sqlite` loses delivery history; the next `tick` then creates one fresh delivery for each currently due note and never replays historical occurrences, so one reminder may repeat but a notification storm cannot happen.
- Effective status is one SQL expression used by `list`, `search`, `recall`, and `tick`: `archived` if stored status is `archived`, else `superseded` if `EXISTS (SELECT 1 FROM relations WHERE relation = 'supersedes' AND dst = notes.path)`, else `active`.

### Incremental sync

Every command on an existing vault begins with `sync.run(vault)`, except `init`, `notifications`, `prompt`, and `pull`, which fetches first and then runs the same sync. The root group runs this pre-command sync once and stores the `SyncReport` in the click context; `notes sync` and `notes check` print that report instead of syncing again. Commands that write Markdown (`new`, `edit`, `relate`, `move`, `draft save`) run a second sync after writing, and that second sync produces their commit.

1. Walk `notes/**/*.md`. For each file compare `(mtime_ns, size)` with the row in `notes`; unchanged valid files are skipped without reading. Files recorded in `invalid_files` are always re-read and re-validated, because their validity can depend on other files (a relation target that was deleted and later restored); they are few, so this costs nothing measurable.
2. Read changed and new files, hash the content (sha256). If the hash matches the stored one, update only `mtime_ns`/`size`.
3. Parse and validate. Valid: upsert `notes`, `note_tags`, `relations` (outgoing), `notes_fts`; delete any `invalid_files` row. Invalid: delete the note's derived rows, upsert `invalid_files` with errors. `deliveries` rows are never touched by sync.
4. Files missing from disk: delete their derived rows and `invalid_files` row. Every valid note that had a relation pointing at a removed file is re-validated in the same run (relation targets are checked against the filesystem, so the referrer becomes invalid until fixed and `notes check` names it). When the target returns, step 1 re-validates the referrer and it recovers without being touched.
5. Steps 1-4 run in one SQLite transaction. The result is a `SyncReport` with `changed`, `removed`, `invalid` (path plus errors), and `unchanged_count`.
6. If `changed` or `removed` is non-empty, or `git status` shows changes in other versioned files, the Git layer stages exactly those valid paths and commits (see Git). Invalid files are never staged, so invalid changes stay uncommitted until corrected. `tick` and `read` skip this step entirely: their sync only indexes, and they never commit or push.

Markdown always wins over SQLite. Commands that change a note write Markdown first and update the index second; if the process dies in between, the next sync reconstructs the row from the file. Invalid Markdown is never left in search as a stale previous version.

`notes sync` prints the report (exit 0 even with invalid files, they are reported as warnings). `notes check` prints every invalid file with `path:line: message` and exits 1 when any file is invalid; it also prints a one-line notice when the packaged `DEFAULTS_VERSION` is newer than `~/.notes/.defaults-version`, without touching vault-owned prompts or templates.

Lemmatization (`pymorphy3`) is loaded lazily and only when a changed note or a query contains Cyrillic tokens, keeping the hook and `tick` fast on the common no-change path.

### Git

All Git operations go through `git.py`, which runs `git` with `cwd` set to the vault via `proc.run_command`.

- `init` (new vault): `git init -b master`, write `.gitignore`, `git add` the initial files, commit `notes: initialize vault`. With a remote: `git remote add origin <url>`, and with `--auto-push` also `git push --set-upstream origin master`; a failed initial push is a warning and is retried by the next auto-push.
- `init --remote <url>` when the remote already has content: `git clone <url> ~/.notes`, then verify it is a vault; a clone that is not a vault is removed again and reported. `git ls-remote <url>` runs first; if it fails, init aborts before creating anything (a remote that cannot be inspected is never assumed empty). Cloning is also the restore and second-device flow.
- Auto-commit after sync: `git add -A -- <changed and removed valid paths> types prompt.md config.toml .gitignore`, then `git commit -m <message>` only if the index has staged changes. Message: `notes: update <path>` for a single file, `notes: remove <path>`, `notes: move <old> -> <new>`, otherwise `notes: sync <n> files`. A commit failure (for example missing identity) is reported on stderr and does not fail the command.
- Auto-push: when `git.auto_push` is true, after the commit step of every command except `recall`, `tick`, and `read`: if the branch has no upstream, run `git push --set-upstream <remote> <branch>`; otherwise run `git push <remote> <branch>` when `git rev-list --count <remote>/<branch>..HEAD` is greater than zero (every commit counts while this machine has no `<remote>/<branch>` ref). The destination is always named, so `branch.<name>.remote` and `remote.pushDefault` cannot redirect the push away from the remote the command reports. When the configured remote does not exist (a vault initialized with `--auto-push` but no `--remote`), auto-push is skipped silently. The push has a 15 second timeout. Failure is a warning; the local commit stays and a later command retries. `recall` never performs network operations because it runs inside the hook's 10 second budget.
- `notes push`: explicit push with the same set-upstream rule; a failure is an error.
- `notes pull`: `git pull --ff-only`; on failure report that history diverged and must be resolved with Git; on success run sync. The CLI never pulls automatically.
- `tick` and `read` change only SQLite; their pre-command sync indexes without committing or pushing.
- A `.git/index.lock` collision is retried once after a short delay.

### Text normalization and search

`textnorm.py`:

- `tokens(text)`: lowercase, `\w+` tokens, length at least 2
- `normalize(text)`: each token containing Cyrillic letters is replaced by its `pymorphy3` normal form (analyzer created once per process, results memoized); Latin tokens are left for the FTS5 porter stemmer; digits are kept; tokens are joined with spaces
- `fts_query(text)`: normalized tokens minus a small built-in Russian and English stopword list, each quoted, joined with `OR`; empty result means "no text search"
- `exact_terms(text)`: raw lowercase tokens matched by `[\w-]+`, used for tag and issue-ID matching so `ATLAS-27` survives intact
- `is_issue_id(term)`: `^[a-z][a-z0-9]+-\d+$`

FTS columns receive `normalize(title)`, `normalize(" ".join(tags))`, `normalize(" ".join(keywords))`, `normalize(body)`. `keywords` should hold synonyms and abbreviations (`Atlas`, `Project Atlas`), not Russian word forms, because the index normalizes those.

Ranking (`search.py`):

- text score `= -bm25(notes_fts, 0, 5.0, 4.0, 4.0, 1.0)` (title, tags, keywords, body weights; higher is better)
- exact tag or issue-ID match: `+10.0` per matched term, reason `issue: ATLAS-27` or `tag: sync-worker`
- path match (recall only): `+recall.path_boost` when `--cwd` equals or lies inside an expanded `paths` entry; a path match alone never makes a note a candidate
- ties broken by path for determinism

`notes search <query> [--limit N] [--all]`: candidates are FTS matches plus exact-term matches. Archived and superseded notes are omitted unless they match an exact term or `--all` is given. Output lines: `[reasons] [id](abs) - Title`, reasons such as `tag: ATLAS-27`, `text`, `superseded`, `archived`.

`notes recall [<query>] [--cwd <path>]` assembles a bounded block in this order and prints nothing at all when it is empty:

1. every currently unread delivery, newest first, reason `unread`
2. exact issue-ID and tag matches for the query's exact terms, any effective status, with the status added as a reason when not active
3. active text matches with total score at least `recall.min_score`, best first

Notes already listed are not repeated, the total is capped at `recall.limit`. The block contains only the H1 title, the clickable path, and deterministic reasons; it never contains generated summaries or note bodies. Human format:

### Schedules, deliveries, notifications

Canonical grammar (`schedule.py`), the only form accepted by validation:

```yaml
schedule: at 2026-09-09T10:00:00+03:00
schedule: every 3 days from 2026-09-02T10:00:00+03:00
```

- `at <timestamp>` is one-shot; `every <positive integer> <minutes|hours|days|weeks> from <timestamp>` is recurring (singular unit names accepted on input, plural always written)
- timestamps are ISO 8601 with a mandatory UTC offset; naive timestamps are a validation error; canonical output always has seconds and a `+HH:MM` offset (`Z` becomes `+00:00`), so travel and database reconstruction never change meaning
- `latest_due(schedule, now)`: for `at T` returns `T` when `T <= now`, else `None`; for recurring returns `anchor + floor((now - anchor) / period) * period` when `now >= anchor`, else `None`; arithmetic is on aware datetimes with fixed offsets
- `normalize_input(text, now)`: accepts canonical text unchanged, plus `in <N|a|an> <minutes|hours|days|weeks>`, `tomorrow [HH:MM]`, `today HH:MM`, `<YYYY-MM-DD> [HH:MM]`, and `every <N> <unit>` without `from` (anchor becomes `now`), interpreted in the local timezone and returned in canonical form; used by `notes new` after the editor closes and by `notes draft save`

`notes tick` (runs sync first):

1. select notes with a schedule and effective status `active`
2. for each compute `latest_due(now)`; skip when `None` or when `deliveries` already has `(path, occurrence_at)`
3. insert a delivery with `delivered_at = now`, `read_at = NULL`
4. run `notify-send --app-name notes "<title>" "<id>"`, then `canberra-gtk-play -i <sound_id>` once when `notifications.sound` is true
5. a failure to reach the notification service or play the sound is logged to stderr; the delivery stays unread and visible to `list` and `recall`; exit code stays 0

Because only the latest due occurrence is considered and `(path, occurrence_at)` is unique, a machine that was off gets at most one delivery and one desktop notification per note per run, the recurrence keeps advancing from its original anchor, and historical missed occurrences are never replayed. During normal operation each recurrence creates a new unread delivery.

`notes read <id>` sets `read_at = now` on every unread delivery of the note and reports how many were closed (zero is not an error). Showing a title in a desktop notification or in the hook never marks it read. A later occurrence makes the note unread again.

`notes notifications enable|disable|status` (`systemd.py`):

- writes `~/.config/systemd/user/notes-tick.service` (`Type=oneshot`, `ExecStart=<absolute path of the running notes executable> tick`, no `WorkingDirectory`) and `notes-tick.timer` (`OnCalendar=minutely`, `Persistent=true`, `AccuracySec=10s`, `WantedBy=timers.target`); stdout and stderr go to the user journal by default
- `enable`: write units, `systemctl --user import-environment DISPLAY WAYLAND_DISPLAY` for the variables that are set, `daemon-reload`, `enable --now notes-tick.timer`
- `disable`: `disable --now notes-tick.timer`, remove both unit files, `daemon-reload`
- `status`: `is-enabled`, `is-active`, next elapse from `list-timers`, and the last five journal lines of the service
- `notes tick` stays portable and can be invoked from cron on systems without systemd; the user timer is the default Linux integration because `Persistent=true` catches missed runs and the user manager has the desktop session

### CLI surface and output conventions

```shell
notes init [--remote <url>] [--auto-push] [--enable-notifications]
notes new <kind> [<title>] [--name <short-name>]
notes draft create <kind>              # context packet JSON on stdin
notes draft list
notes draft show <draft-id>
notes draft revise <draft-id> [<feedback>]   # feedback from argument or stdin
notes draft save <draft-id> [--name <short-name>]
notes draft discard <draft-id>
notes edit <id>
notes show <id>
notes search <query> [--limit <n>] [--all]
notes recall [<query>] [--cwd <path>]
notes list [--unread] [--kind <kind>] [--status <active|archived|superseded>] [--tag <tag>] [--path <path>]
notes read <id>
notes relate <id> <supersedes|child|related> <other-id>
notes move <id> <new-path>
notes sync
notes check
notes tick
notes push
notes pull
notes prompt <kind>
notes notifications <enable|disable|status>
```

- `--json` is accepted by every command (a shared decorator) and produces a stable machine representation: an object or array on stdout on success; on failure an object `{"error": {"type": "...", "message": "..."}}` on stderr with exit code 1
- exit codes: 0 success, 1 `NotesError` (validation, missing vault, generator failure, divergent history), 2 usage error (click default); `notes check` exits 1 when any file is invalid
- human output includes the title and a clickable absolute path; Markdown and SQLite use relative paths
- IDs are printed as vault-relative paths; input accepts vault-relative paths, absolute paths inside the vault, and bare filenames under `notes/`
- `list` filters use effective status, so `--status superseded` works; filters combine with AND; unread notes are listed first, then by creation date descending; `--path` matches notes whose expanded `paths` entry equals or contains the given path
- `new`: title from the argument or an interactive prompt; `--name` gives the short name, otherwise an editable suggestion (the title truncated to seven words) is offered in a terminal and used silently otherwise; the dated Unicode slug is built (lowercased, runs of non-alphanumerics become `-`, Unicode and Cyrillic preserved, collisions get `-2`, `-3`, ...); the file is created from the kind template; kinds whose validation requires `schedule` are asked for one; `$VISUAL`/`$EDITOR` opens the file when a terminal is present; afterwards `schedule` is normalized if it is relative, the file is validated, synced, and committed; an invalid result is reported with line numbers and left uncommitted
- `edit`: opens the note in the editor, then sync and commit as for `new`
- `show`: prints the file verbatim; `--json` gives metadata, effective status, unread count, and body
- `move <id> <new-path>`: `new-path` must be under `notes/`, follow the dated filename rule `YYYY-MM-DD-<slug>.md`, and not exist; renames with `git mv` (plain rename when untracked); rewrites the moved note's outgoing targets and every incoming `note:` field in other files through the round-trip rewriter; updates `deliveries.path`; syncs and commits
- `relate`: validates the relation name, that both notes exist, no self-relation, no duplicate; appends to `related` (creating the key) with a path relative to the source file; syncs and commits
- `prompt <kind>`: prints the shared prompt, the kind prompt, and the kind template composed as the generator would receive them (without a context packet)

### Prompts, templates, generator, drafts

The vault owns prompts and templates; they are regular versioned files editable without changing a skill or reinstalling the CLI:

- `~/.notes/prompt.md`: shared instructions for every kind: use only facts from the packet and never invent new ones, prefer existing tags from the provided list, write `keywords` as synonyms and abbreviations, write `schedule` in canonical form, produce a concise five-to-seven-word short name, return exactly one JSON object `{"short_name": "...", "markdown": "..."}` and nothing else, and conditional follow-ups after saving (offer to draft a concise tracker comment when the note references a tracker issue and contains durable team-relevant information; never suggest publishing personal reflections; never write to a tracker without explicit user approval)
- `~/.notes/types/<kind>/prompt.md`: what to capture and how to reason for that kind
- `~/.notes/types/<kind>/template.md`: the mechanical scaffold used by `notes new` even without an agent

`notes init` installs the packaged defaults. Later CLI versions report newer defaults through `notes check` and never overwrite vault-owned files.

Generator (`generator.py`):

- `compose_prompt(vault, kind, context=None, previous=None, feedback=None)`: shared prompt, kind prompt, kind template, the vault's existing tags and kinds, the context packet as pretty JSON, and for revisions the previous Markdown plus the feedback
- `run(config, prompt)`: runs `config.generator.command` as an argument array (never a shell string) with the prompt on stdin, stdout captured, stderr inherited for diagnostics, `timeout_seconds` enforced; a non-zero exit or timeout raises `GeneratorError` and leaves no partial draft
- `parse_envelope(stdout)`: accepts the whole output as JSON, else the first fenced ```json block, else the last balanced top-level JSON object containing `"markdown"`; requires non-empty string `short_name` and `markdown`
- the packaged default command is Codex (`codex exec ... -`); any executable or wrapper around Groq, a local model, or another provider works if it honors stdin prompt in, JSON envelope out

Drafts (`drafts.py`), stored under `~/.notes/drafts/<draft-id>/` and never indexed or searched:

- `draft-id` is `<YYYYMMDD-HHMMSS>-<kind>` with a numeric suffix on collision
- files: `draft.json` (`id`, `kind`, `short_name`, `created_at`, `updated_at`, `revisions` as a list of feedback strings), `context.json`, `draft.md`
- `create <kind>`: reads a JSON object from stdin (anything the skill considers relevant: facts, paths, tags, keywords, references, schedule, cwd), composes the prompt, runs the generator, stores the draft, prints the id, short name, and draft path
- `show`: prints `draft.md` (with metadata under `--json`); `list`: one line per draft
- `revise <id> [<feedback>]`: re-runs the generator with the previous Markdown and the feedback, overwrites `draft.md`, appends to `revisions`
- `save <id> [--name]`: normalizes a relative `schedule`, fills a missing `kind`, validates the Markdown exactly like sync does (errors are reported and the draft is kept), builds the filename from the save date and the slug of the short name, writes the note, syncs, commits, deletes the draft directory, prints the new id
- `discard <id>`: deletes the draft directory
- generation is synchronous from the CLI's perspective; Claude runs it in the background so the conversation can continue

User confirmation is the trust boundary: an unconfirmed draft never participates in search or automatic injection.

### Agent integration

The plugin lives in `plugin/` (plugin name `notes`, so skills are `/notes:capture`, `/notes:decision`, `/notes:reminder`, `/notes:recall`). Skills are reserved for operations that need contextual understanding; simple operations like `!notes read <id>` need no skill.

- `hooks/hooks.json`: `UserPromptSubmit` runs `sh "${CLAUDE_PLUGIN_ROOT}/hooks/recall.sh"` with a 10 second timeout; `recall` stays inside that budget because it never pushes or pulls and loads `pymorphy3` only for Cyrillic queries
- `hooks/recall.sh`: exits 0 silently when `notes` is not on `PATH` or the vault does not exist; otherwise extracts `cwd` and `prompt` from the stdin JSON with `jq` and runs `notes recall --cwd "$cwd" -- "$prompt"`; whatever it prints becomes context for Claude, and an empty result injects nothing
- each `SKILL.md` has a short, precise description so skill reminders can activate it, and follows one procedure: extract facts, paths, references, tags, and keywords from the session; ask one targeted clarification question only if critical context is missing; run `notes prompt <kind>` to learn what the kind expects; write a compact fact packet (never the transcript) to `notes draft create <kind> --json`, in the background; present the draft with `AskUserQuestion` (save, revise with free-form feedback, cancel); then `notes draft save`, `notes draft revise`, or `notes draft discard`
- `/notes:recall` uses `notes search --json` and `notes recall --json`, then reads the chosen notes with `notes show` before reasoning about them
- installation for development: `claude --plugin-dir ./plugin`; permanent installation through a local marketplace entry, documented in the README
- the directory is `plugin/`, not `claude-plugin/`: Codex reads this same layout, `.claude-plugin/marketplace.json` and `.claude-plugin/plugin.json` included, and resolves the entry to the same directory, so one plugin serves both agents and no `codex-plugin/` counterpart is needed. Codex's own native format (`.agents/plugins/marketplace.json`, `.codex-plugin/plugin.json`) is only worth adding if it ever gains metadata this plugin needs

### Acceptance scenarios

These become the scenario tests in Task 24.

1. **Create and search from the CLI.** `notes init --auto-push`, `notes new decision "Project Atlas task updates over Kafka"` with a fake editor suggests a short name, creates the dated path, validates, indexes, and commits. `notes search "why doesn't Project Atlas communicate with the backend over WebSocket"` returns the note with its title and clickable absolute path, ranked by tag, keyword, and text matches.
2. **Create a decision through the draft flow.** A context packet on stdin to `notes draft create decision` with a fake generator produces a draft; `notes draft revise` applies feedback; `notes draft save` writes the note, indexes it, commits it, and removes the draft. A failing generator leaves no draft and no note.
3. **Work manually without an agent.** A file written directly into `~/.notes/notes/` with frontmatter and Markdown is validated by `notes check` and listed by `notes list`, which synchronizes automatically; a commit is created locally; with a fake unreachable remote and `auto_push`, the push fails as a warning and succeeds on a later command once the remote is reachable.
4. **Receive a reminder.** A reminder with `every 3 days from <anchor>` produces exactly one delivery, one `notify-send`, and one sound at the first `tick` after the anchor, none on the next tick within the same period, and one more after the period elapses; a `tick` after a long gap creates one delivery only; `notes recall` lists it under `Unread notes` until `notes read` closes it; the next occurrence makes it unread again.
5. **Return to an old decision.** A new note with `related: [{relation: supersedes, note: <old>}]` gives the old note effective status `superseded`; `notes recall "ATLAS-27"` finds notes tagged `ATLAS-27` with reason `issue: ATLAS-27`; default `search` prefers the active note and omits the superseded one unless matched exactly or `--all` is given; `notes list --status superseded` shows it; the old file's content is unchanged.

### Review round 1 fixes

- `document.rewrite_frontmatter` writes through the new `document.write_atomically`: a temporary file in the note's directory, fsynced, given the mode of the file it replaces, then `os.replace`. An interrupted `relate`, `move`, schedule normalization, or draft preparation now leaves the note as it was instead of truncating it, which is what the Solution Overview promises.
- `schedule.Recurring` validates its period on construction, so `every 1000000000 days from ...` is a grammar error instead of a note that passes validation and makes every `notes tick` raise `OverflowError` on `period`. `normalize_input` maps the same overflow, and a delay that lands past `datetime.max`, to the `ValueError` its callers already handle.
- `slug.create_dated_note` creates the file with `O_EXCL` and takes the next suffix on `FileExistsError`, so two concurrent `notes new` or `notes draft save` runs with the same short name produce two notes instead of one that silently loses a writer. `slug.dated_filename` stays for the name a draft is validated under; only the numeric suffix can differ from the name the create claims, and no validation rule depends on it.
- `notes move` migrates the deliveries straight after the rename, before rewriting the references in other notes, so an interruption during that rewriting cannot strand unread deliveries under the old path. The remaining window (a machine that dies between the rename and one SQLite transaction) is accepted: a rename journal or a note identity independent of the path is a subsystem this vault does not need.
- `recall.limit` must be a positive integer (`config._Section.positive_integer`); a zero or negative value used to be applied as a slice and printed nearly every note.
- `hooks/recall.sh` cuts the prompt to its first 4000 characters before passing it as one argument, because Linux refuses to exec an argument past 128 KiB and a pasted file would fail the hook. The opening words are what a bounded recall block needs, so a stdin query mode for `notes recall` was not worth the CLI surface.
- Accepted as it is: `notes draft save` still deletes the draft after the note is committed, so a process killed in between leaves a draft that a retry saves again under a `-2` name. Persisting the target in the draft metadata buys little against a window of microseconds, and the duplicate is visible and deletable.

### Gate round fixes

- Every push names its destination: `git push -q [--set-upstream] <remote> <branch>`, and `unpushed_count(vault, remote, branch)` counts `<remote>/<branch>..HEAD` (the whole branch while this machine has no such remote-tracking ref) instead of `@{upstream}..HEAD`. A `[git] remote` that is not the branch's upstream remote, or a `remote.pushDefault` in the user's global configuration, used to send the commits somewhere other than the remote `notes push` reported, and "nothing to push, `<remote>` is up to date" could be about a remote that had received nothing. `push_pending` now also returns `None` for a remote that is not configured in the vault even when the branch has an upstream, so auto-push stays silent and `notes push` says which remote to add. The design bullet under Git was incomplete, not the implementation; it has been corrected.
- A `git mv` onto a path that is still invalid is unstaged whole. `git status --porcelain -z` reports a staged rename as one entry under its new name followed by its origin, which `_parse_status` used to discard, so unstaging the invalid new path left the deletion of the old one staged and `notes move` committed (and auto-pushed) the note's disappearance under `notes: move <old> -> <new>` while telling the user the note "stays uncommitted". `StatusEntry` now carries `orig_path`, and both halves of such a rename are reset and kept out of `git add`, so the note keeps its place at `HEAD` and the repaired move is committed by the next sync as `notes: sync 2 files`. The rewritten referrers are still committed, as they are for an untracked invalid note. `tests/unit/test_git.py` and `tests/cli/test_move.py` encoded the old outcome and were rewritten around the new one.
- `notes new` and `notes draft save` clear the delivery rows of the path they claim (`deliveries.clear`, the rule `deliveries.move` already applies to its destination). Sync never touches `deliveries`, so a note deleted by hand leaves its rows behind, and a later note on the same day with the same short name lands on exactly that path; it used to inherit the unread state and could have its first occurrence suppressed as already delivered. `O_EXCL` guarantees the path was free, so the rows can only be orphans. Sync still leaves the table alone: rows must survive a temporarily missing or invalid file.

## Changes After v1

**2026-09-04, the kind set shrank from six to four:** `event` merged into `fact` and `promise` merged into `reminder`, leaving `decision`, `fact`, `reminder`, `idea`.

The plan sized the kind set by what a personal vault might want to record. The binding constraint turned out to be agent triggering: an agent picks a kind from a single user utterance, so two kinds are worth keeping apart only when the utterances that produce them are distinguishable. `event` failed that test, since every sentence reporting an occurrence also asserts a fact, and plugin/skills/capture/SKILL.md said so itself by calling both kinds "the default". `promise` passed the test (a commitment names another person), but was merged anyway on the principle of Task 23's minimal model: the kind is worth reintroducing when a real vault shows the need, not before.

What went with them: the one-shot rule for a promise schedule (`schedule_problem` now takes only the text and checks the grammar), the `**Owner:**` and `**Due:**` sections, and the `**What happened:** / **When:** / **Consequences:**` sections. The absorbed guidance moved into the `fact` and `reminder` prompts: a fact records what happened with its date and consequences, and a reminder covers a commitment by naming the person in the action and using a single moment. `DEFAULTS_VERSION` went to 2.

**2026-09-04, one drafting skill per kind:** `capture` was replaced by `fact` and `idea`, and `note` was added for the kinds a user installs under `~/.notes/types/`. The plugin now ships `decision`, `fact`, `idea`, `note`, `recall`, `reminder`.

Task 23 gave the four kinds without their own skill to one catch-all, which then picked the kind in step 1 of its own body. That puts the decision in the wrong place: a skill is selected by matching its description against the user's words, so the kind is already implied by the phrasing that triggered the skill, and a catch-all throws that signal away and re-derives it. It also forces the catch-all's description to enumerate four kinds, which by skill-creator's rule that a description must fit two terse sentences is the signal to split.

Each kind skill now fixes its kind, names the trigger phrases of that kind, and points at the sibling skills of the kinds it competes with, so the descriptions read as disjoint families rather than four variations on "capture something". `note` is the deliberate exception: it takes the kind from `ls ~/.notes/types/` and its shape from `notes prompt <kind>`, because only the vault knows a user-added kind. Adding a kind now means adding a skill, which is the cost that keeps the kind set small.

**2026-09-14, whole summaries in group help and coloured human output:** `notes --help` (and the `draft` and `notifications` groups) listed each command with click's 45-character cut and a trailing `...`; the groups now print the whole first paragraph of each command's help, wrapped to the terminal. The human lines of `list`, `search`, `recall`, and `tick` are coloured on a terminal (kind cyan, status green/dim/magenta, `[unread]` bold yellow, reasons blue, `delivered:` and the recall headings bold green, titles bold), following `NO_COLOR` and `FORCE_COLOR`, and `notes list` pads its kind and status columns to the widest value in the listing, with the `[unread]` column present only when some note is unread. The text under the colour is unchanged, so the hook, pipes, and the tests see the same lines. Both came from the idea note "Improvements for 'notes'".
